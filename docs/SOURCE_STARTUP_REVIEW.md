# Read-only startup/storage review

Reviewed pinned EHR v8.0.3 commit `ce23f0d050f617a59507e5bb0fbfff751d4b5134` through the selected protected+mobile `EHR-iOS-source-app-stage/RoleInfo33/EHR.csproj`, selected `JSON32/source/Main.cs`, `Release32/source/OptionHolder.cs`, current source application/host, and canonical native full-runtime binding order. No account, lobby, login, terms, or game operations were performed by this review.

The actionable failure path is `EHRSourceApplication.Load`: `plugin.Load` creates real source components and invokes Finished/Main.Start before final callback binding/activation. `Failure` only records status. The source host's catch removes its loader registration but does not destroy Unity state. Original Main creates Coroutines and ClientControlGUI early; logging can start the persistent logger coroutine, and Main.Start starts news/tag fetch coroutines. A later failure therefore needs the native failure-only cleanup in this package. It preserves the original failure status, disables source callback dispatch first, and does not retry the failed plugin.

The native startup order binds actual full-module facade/delegate/original/patch tables, production coroutines, exact static source classes and all-seven factory profile, touch renderer, and exact compiled target selectors before source application prepare/load. Prepare checks passive target availability without invoking target bodies; Load checks every installed candidate before source side effects. Compilation and passive binding do not prove Main.Load's transitive native leaf calls; `AmciRegistration.Apply` is one uncaught in-memory native mod-registration field write during Load, rather than an official progress write.

The native caller supplies `NSApplicationSupportDirectory/EHRSource` and the verified full NativeAOT module's absolute path. SourcePluginHost publishes these paths before constructing Main, uses the real BepInEx.Core configuration file under `EHRSource/config`, and logs under `EHRSource/logs`. Main.DataPath is adapted to the host-owned root. The traced startup writers (translations, template/banned-word migration, mod lists/tags, role colors, options/user data and achievements) stay under Main.DataPath, including `EHR_DATA`, `Language`, `BepInEx/log.html`, and `OriginalRoleColors.json`. This is broader than the literal `EHR_DATA` subdirectory but stays in the dedicated EHRSource tree. The selected mobile adaptations skip Steam appid creation on iOS and keep log export/cleanup under this root. This is a control-flow/path review, not a complete filesystem or engine side-effect proof.

Canonical `EHRSourceAccountPolicy` excludes six exact callbacks before Prepare and again in the active binding predicate: privacy Show/Close, forced free-chat, forced canOnline, banPoints reset, and saved onboarding-warning changes. No direct Main.Load call to those bodies was found. Their compiled presence is not invocation; the exclusions must remain keyed to the pinned descriptor IDs.

One remaining official preference mutation is `EHROnlySearch.FilterTagManagerPatch.Postfix`: it adds `EHR` to `DataManager.Settings.Multiplayer.ValidGameFilterOptions.FilterTags` when RefreshTags runs. It has no explicit Save and is not an account/progress reset; it means the selected full source does not promise zero mutation of all vanilla UI preferences. MainMenuManager also hides its existing AccountWindow visual panel in a menu callback; this does not modify account state. Neither path was invoked by the review.

The failure cleanup is intentionally narrow. It does not erase source mod data, undo already completed configuration/log writes, unload metadata, remove native pre-sign entrypoints, restore source static fields, or claim rollback of a loaded plugin. It leaves original native methods callable with source dispatch disabled. The first real full startup and vanilla-client hosting/role playtests remain separate runtime gates.
